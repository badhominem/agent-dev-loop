# Agent Dev Loop

A visual, convention-driven way to build software with AI agents. People decide
what the system should do and approve a picture of the change; agents build
inside that picture; review starts from a picture, not a wall of text.

Works with Claude Code and GitHub Copilot CLI. Python projects first.

## The loop

| Stage | Who | What happens | Command |
|---|---|---|---|
| Intake | you | Add a demand to the queue | `loop new "Dedupe orders"` |
| 1 · Plan | planner, live with you | Interview in rounds, Gherkin scenarios, a plan, the change view | `loop plan 0001` |
| Approve | you | Fix the plan as the contract and record its base commit | `loop approve 0001` |
| 2 · Build | outside-test writer, then builder | Tests from the scenarios first, then code until they pass | `loop build 0001` |
| 3 · Review | scripts, then reviewer | Measure, sort findings, draw plan vs actual, write the PR | `loop review 0001` |
| 2 + 3 | | Build and review, sending work back automatically up to 3 rounds | `loop run 0001` |

Every agent runs as its own fresh session in the demand's own git worktree.

## Install

```bash
pip install -e path/to/agent-dev-loop     # puts `loop` on your PATH
cd your-repo
loop install --harness claude,copilot      # loop/ folder, AGENTS.md, harness files
loop onboard                               # existing repo: draft component files + system map
```

Then open `.loop/onboard/report.html`, write each component's responsibility in
`loop/components/`, tighten `may_depend_on`, remove `uncertain: true`, and commit
to your truth branch as `loop: onboard`.

Requires Python 3.11+ and git. Projects need `pytest` and `pytest-bdd` for the
default test command; change `test_command` in `loop/conventions.yaml` otherwise.

## What goes where

```
loop/                     committed, human-readable
  principles.md           P1–P9, read first by every agent
  conventions.yaml        truth branch, harness, size limit, component level, table rules, zones
  tools.toml              which shell commands agents may run (allow / ask / deny)
  worktree.toml           files to copy and setup commands for new worktrees
  context.yaml            lasting project facts, saved only with approval
  components/<id>.yaml    component index: opinions only (facts are read from code)
  behaviour/*.feature     behaviour index: one Gherkin file per capability
  demands/<id>/           demand.md, status.yaml, grilling.md, plan.yaml, edits/, build.yaml
  agents/<role>.md        optional: your own version of an agent's instructions
.loop/                    ignored by git: views, findings, reports, command log
.claude/  .github/        generated by `loop install`, don't edit by hand
```

## How agents are kept in their lane

`loop` starts each agent with `LOOP_ROLE`, `LOOP_DEMAND` and `LOOP_ROOT` set. The
guard hook (`loop guard`, installed for both harnesses) runs before every tool call:

- **File writes** are allowed only inside the role's zones (see `zones` in conventions).
  The builder can't touch tests; nobody can touch `principles.md`, `conventions.yaml`
  or `tools.toml`; nothing may be written outside the demand's worktree.
- **Shell commands** are split on `&&`, `||`, `;` and `|`, and each part is checked against
  `tools.toml`. The longest matching prefix wins. "Ask" commands are blocked when an
  agent runs on its own, so it must stop as blocked instead.
- **Every call is logged** to `.loop/commands.log`.

Outside a `loop` session only the deny list applies, so normal use of your
harness is unaffected.

## Components and boundaries

`component_level: auto` (default) makes each module directly in a top package a
component and each sub-package one component. `package` and `module` are the
alternatives. Each component file has a `boundary` that groups it on the map;
onboarding fills in a default you can change. Maps with more than
`view_max_nodes` components are drawn one box per boundary.

Tables are found through `table_rules` (calls like `read_rows("raw.orders")`) and,
optionally, `sql_tables: true` for SQL strings.

## Status and limits of 0.1

Tested here: 38 automated tests, including a full loop run with a stand-in harness,
the guard against both Claude and Copilot payload formats, and onboarding of two
real open-source packages. `ruff` and `mypy --strict` pass.

Not yet tested against live agent sessions. Before relying on it:

- Run one demand with each harness and check `.loop/commands.log` to confirm the
  guard sees every tool call. Tool names and argument fields differ per harness;
  the guard knows the common ones (`Bash`/`bash`, `Write`, `Edit`, `create`, `edit`,
  `apply_patch`...).
- Copilot CLI also reads Claude-format hooks, so with both installed the guard runs
  twice in Copilot. That's harmless, but the log shows each call twice.
- Detecting file writes inside shell commands is best effort (redirects, `tee`, `cp`,
  `mv`, `rm`, `sed -i`). A script an agent writes and then runs isn't covered by
  the hook; dev-only credentials are the real safety net.
- In Copilot, the interactive planner session doesn't receive a first message; it
  starts by reading `.loop/session.yaml` as its instructions tell it to.
- The boundary map has no drill-down yet.
